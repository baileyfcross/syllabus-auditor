# Syllabus Auditor - Passwordless native desktop, optional startup lock

This patch affects only **native desktop launches** (Windows WebView2 and macOS Cocoa). The normal browser/Docker deployment continues to require its existing login and session security.

## Apply

1. Stop Syllabus Auditor and back up your existing `data/` folder. Installed desktop application user data is under `%LOCALAPPDATA%\SyllabusAuditor\data` on Windows; on macOS, `~/Library/Application Support/SyllabusAuditor/data`.
2. Extract the ZIP **into the project root** (the folder containing `app/`, `packaging/`, and the Windows launchers), replacing matching files.
3. Keep the previous course-title, Next unreviewed, and Tailwind patches applied. This ZIP's `app/static/app.js` builds on those earlier UI changes. No Python requirements, desktop build flags, or Tailwind configuration need to change.
4. On Windows, preview with `".\Start Syllabus Auditor Desktop.bat"`, or rebuild your installer with `".\Build Windows Installer.bat"` and reinstall it.
5. On macOS, if you have already installed the macOS packaging kit, rebuild using your `packaging/macos/build-macos.sh`. This update also includes its corresponding native launcher.
6. Start the desktop program. The local dashboard should appear without a username, password, or first-run setup token.

## Optional password on startup

Open **Settings > Desktop security > Require password on startup** and enter a password of at least 12 characters. Restart the app to test the password lock.

The local username is `desktop-local` and is prefilled on the desktop login form. You can change the password from Settings after unlocking.

Select **Turn off startup password** in the same settings screen to restore automatic login at the next launch.

**Important:** This password controls entry through the application; it is **not disk encryption**. Anyone with privileged access to the operating-system account, backups, or the local database may access stored data. Use OS login, device encryption, and appropriate filesystem permissions on shared machines.

## What changed

- `app/desktop_auth.py` (new): native-only random one-time startup secret, default passwordless identity and lock preferences.
- `app/main.py`: desktop-only one-time session endpoint, optional password preferences, retained session/CSRF protections, and separate hosted authentication.
- `app/static/app.js`: desktop no-login loading state, local-user header, password-lock settings; hosted login unchanged.
- `packaging/windows/desktop_launcher.py`: generates a new secret per launch, authenticates inside WebView2 using a header and an HttpOnly cookie, never passes the secret in a URL.
- `packaging/macos/desktop_launcher.py`: same for Cocoa; Mac native code must still be tested on macOS.
- `tests/`: new security tests and updated launcher tests.

The desktop uses the same SQLite tables and keeps every existing institution, course record, uploaded syllabus, audit, and report. It creates a reserved local administrator account `desktop-local` with an initially random password. Existing application accounts remain in the database. This account is blocked from normal hosted login.

## Safety design

The local backend still requires an authenticated session and CSRF token for protected operations. A random 48-byte secret, generated by the **native launcher**, is used exactly once to establish that session in the native window. Other local processes cannot log in just by knowing the loopback port. The server listens on `127.0.0.1` only; the unlock endpoint is unavailable when the hosted process has no native-launcher secret. Stored sessions are invalidated on each desktop startup to enforce the optional lock.

If the startup password is forgotten, a recovery workflow is not implemented. Back up your data before enabling a lock. Deleting `desktop-preferences.json` would turn off this *application-level* lock for a person who already has unrestricted filesystem access, which is why it should not be treated as strong protection against a compromised OS account.

## Test commands

```sh
python -m pytest tests/test_system.py tests/test_desktop_authentication.py tests/test_desktop_launcher.py -q
node --check app/static/app.js
```

Windows EXE/installer and macOS APP/DMG must be smoke-tested on their target operating systems. This patch has been checked by automated backend and launcher tests in a Linux environment, not by running the graphical app on Windows or macOS.
